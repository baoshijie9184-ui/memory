评审草案

逻辑上车控记忆与 Skill 独立检索，物理上先共用 PostgreSQL 和逐表 JSON Mirror。结构化车控/行程及常规条件查询目标为 0 次额外 Qwen；Hermes 只预留离线插件，不进入 V1 在线链。详见 V1 方案收口文档。

V1 字段评审 1 · 车控请求与结果

两个受限事件类型、一个必填操作关联键；不强迫上游额外提供事件 ID。

拟定接口

请求上报 operation_id / tenant_id / user_id / vehicle_id / source / tool_name / args / requested_at；结果上报 operation_id / tenant_id / vehicle_id / result_status / result_at，确有车端终态回执时补 vehicle_completed_at，失败可附 failure_stage/error_code。operation_id 关联两阶段；默认按 (tenant_id, operation_id, phase) 与内容摘要幂等，event_id 可选；同阶段不同内容不盲覆盖，交由对账。乘员、trip_id、interaction_id、天气等上下文只在可信上游提供时保存。服务端以认证 scope 校验身份，以 Tool Registry 校验参数；回执先到可暂存但不能声称成功，unknown/failed 不算成功 Skill 证据。详细 JSON 示例见 V1 基线；当前代码未实现此接口。

发送失败的两层兜底

可靠重试的是上报记忆的事件，不是物理车控动作。

上游契约待确认

车控命令未送达：沿用发送前创建的 operation_id，结果为 failed / failure_stage=dispatch，无车辆完成时间；送达后车端执行失败则为 failure_stage=execution。若是上游向记忆服务上报失败，上游需要持久化 Outbox 并按同一操作 ID/阶段重试，记忆端幂等和对账。无终态回执可标 unknown；记忆系统不会自动重发车控命令，也无法凭空找回上游从未持久化的上报。

V1 字段评审 2 · 一趟行程

可信身份先于画像归属，行程事实先于通勤规律。

拟定接口

按稳定 trip_id 幂等更新一条 Trip 行：最少 tenant_id / vehicle_id / source / started_at / status；结束时间、可信 driver_user_id、地点标签和 context 可选。in_progress 后补 completed/aborted，无终态可标 unknown；旧状态不能覆盖新状态，冲突需对账。没有可信驾驶员身份只留车辆级历史，不能归入个人 Profile；没有可信目的地不能编造“去了哪里”。不存完整 GPS 轨迹，每趟不增加 Qwen/BGE。示例见 V1 基线；当前代码尚无行程接口和表。

V1 边界评审 3 · Tool Registry 与执行权限

上游定义工具与权限，记忆系统消费版本化目录并保存可追溯候选。

对接待确认

上游提供只读版本化工具目录（tool_name / schema_version / args_schema），记忆侧缓存验证参数；新工具未同步时可信原始操作先受限保存为 unverified，不丢历史、也不进入可执行 Skill 或当前偏好。记忆侧 Attribute Registry 只映射已验证参数，不发明车控能力。上游 Policy/Permission 独立决定 allow / confirm / deny、授权撤销与实时安全，记忆入库不逐条调用它；Skill 即使 published 也只是建议。具体目录同步与权限接口仍待上游确认，详见 V1 基线。

V1 字段评审 4 · 条件来源与缺失值

条件可扩展，但可执行匹配只使用有来源、时间和类型校验的数据。

拟定契约

context 可包含天气、时区、工作日/周末、季节、车辆状态和乘员；可用于车控的每个条件带 value/source/observed_at。工作日可在可信时区下计算，天气取可信上游且需检查时效；驾驶员身份不明时不归入个人习惯。未知条件不阻止真实 Operation/Trip 入库，但不能被当成已满足的条件；受限 Skill 返回缺失/需确认，不让模型猜。普通条件处理不新增 Qwen 调用。

真实上游对接：目前证据不足

本地仓库未提供车控/行程生产 payload，所有新 JSON 均为设计 DTO，不是已验证接口。

需要上游样例

现有 FastAPI 只有对话写入与记忆搜索；代码中未见应用层鉴权或认证身份与 body scope 的对照，云端网关是否承担该职责尚未知。车控/行程应通过可插拔 Input Adapter 映射真实上游字段，保留来源与 Schema 版本；缺失操作 ID、终态或可信驾驶员身份不得由 LLM 补造。新接口开放前必须确认身份边界，并取得脱敏的请求/回执/行程样例和 Tool Registry、Permission 说明。详细核对见 V1 基线第 8 节。

设计冻结候选

输入与信任

统一 Operation 支持 command 的请求/结果和 observed_action 的可信单次动作，不伪造缺失请求；身份、作用域、工具结果和环境条件分别校验。上游 Tool Registry 定义 Schema/结果来源，Policy 独立决定逐步授权。

存储与回放

开放 Profile 与轻量条件 Preference 双轨；Operation、Trip、Episode、Skill 保留证据与版本。模拟 18 条车控事件应归并为 9 条操作，镜像复用 Outbox，但现有全量 Reconciler 尚未实现，不能声称端到端验收通过。

来源边界：Mem0/StructMem/FluxMem/memU/MIRIX/TiMEM/Memos 分别提供过程记忆、事件连接、技能蒸馏、画像或 Tag/时间启发；车载可信结果、跨人隔离、条件槽位、双轨偏好和授权分离是我们的改造。完整对照见契约文档第 1 节。

Fact 四类：Mem0 借鉴与我们的改造

原版 Mem0：当前本地开源版的 additive extraction 从新消息抽取有上下文的自然语言记忆，输出主要是 text 与关联历史记忆的 linked_memory_ids；它不要求输出下面四种 fact_type，也没有我们的“Topic Facts → 显式 Event”链路。我们借鉴其新消息抽取、历史关联和避免无证据推断的思想，并非原样复用其输出契约。

我们的新增分类：action＝一次具体请求/操作（如“用户请求播放周杰伦”）；state＝有回执支持的实际状态（如“车辆正在播放《晴天》”）；explicit_preference＝用户明确表达的喜欢、习惯或舒适设置；personal_fact＝用户明确提供的身份、关系、工作或计划等信息。一次普通播放请求只属于 action，不能推断成“喜欢周杰伦”。

谁来判定：完成一个 Topic 后，Qwen 在一次调用中抽取零条或多条 Fact，并给每条选择类别、来源消息编号、语义 Tag 和新旧操作。代码只校验类别/来源是否合法，并强制 action 为 ADD；目前不会二次验证语义分类的正确性。

为何增加：车载场景必须区分“用户提出操作”和“车机实际执行”，避免把一次行为误写成长期偏好；区分稳定事实与发生记录也便于后续 Event 聚合、时间检索和 Profile 蒸馏。代价是增加了固定分类边界及误判风险；保留原消息证据，后续用评测检查并调整分类，不额外增加一次 LLM 调用。

输出示例：{"memory":[{"text":"用户请求播放周杰伦的歌曲","fact_type":"action","operation":"ADD","attributed_to":"user","source_message_numbers":[0],"semantic_tags":["音乐","周杰伦"]},{"text":"车辆正在播放《晴天》","fact_type":"state","operation":"ADD","attributed_to":"assistant","source_message_numbers":[1],"semantic_tags":["音乐","晴天"]}]}。入库后两条分别成为 memory_items 中的 FACT 行：content 保存文本，metadata.fact_type 保存类别；代码补上时间、向量、Topic/Message 证据关系与 Tag。

借鉴与差异

StructMem 的同 Topic 基础条目是隐式 Event；我们额外持久化显式 Event 与向量，便于跨会话检索和精确追溯。TiMEM 以高层 Persona 文本为主；我们拆成开放 Profile 与固定 Preference 两种消费视图。

专题 · 行程、条件偏好与控车 Skill 候选（待确认）

这是下一阶段设计讨论，不表示当前代码已实现。历史行为、偏好和执行授权必须分开。

待确认设计

写入与沉淀

结构化行程和工具回执 → 带 trip_id、时间、车辆、操作者、成功/失败状态的 Event；Event/Cross-Event → 带天气、季节、工作日/周末、车辆等适用条件的 Preference；多次成功操作或用户明确要求 → 可插拔 Skill Distiller 产生候选操作模板。第一版可确定性聚合结构化日志，不增加 Qwen 调用。

三种对象分别回答：Trip/Event“发生过什么”；Profile/Preference“什么条件下喜欢什么”；Skill Candidate“常按什么步骤操作”。不能由一次操作直接推断长期偏好或自动执行授权。

候选模板与安全边界

intent + ordered_steps(tool_name, parameter_source) + conditions + scope + supporting_event_ids + status。例如冬季工作日、V1 上“空调 22℃→座椅加热”；夏季 24℃是另一条件偏好，不覆盖冬季值。检索先匹配当前条件和身份，车机 Agent 再依据实时状态、显式授权及安全策略决定建议、确认或执行。

通知/免打扰与“哪些操作可自动执行”属于显式用户设置或独立权限配置，不能从历史习惯推断。失败、撤销和人工纠正需作为反证。启用阈值、有效期、行程输入范围、权限接口均待讨论。

参考：AWS Episodic Memory 的 episode/reflection、AWS User Preference 的提取/合并、LangGraph procedural memory 的程序性记忆概念；车控条件模板与权限边界是 DesayMem 的场景改造。详细讨论同步记录于 DESIGN_DISCUSSION_LOG.md。

补充对照 · Procedure / Skill 的借鉴边界

下列是本地代码核对后的取舍；我们的 Skill 仍属于待确认的增量设计。

不代表已编码

别人怎么做

Mem0 的实际入口为 memory_type="procedural_memory"，对 Agent 轨迹单独生成完整文本摘要并嵌入；本地源码未发现 procedure_type。memU 将 Skill 和用户记忆分轨，按 session 的工具调用决定不做、更新旧 Skill 或创建 Markdown 文件；MIRIX 用 entry_type / summary / steps[] 独立存程序性记忆；FluxMem（LightMem 仓库内另一模块）离线聚类 Episode、由 LLM 归纳 Skill，并用来源边及回放评分维护。

我们为何只取一部分

车控 Skill 既要继承“分轨、步骤、来源、版本”，又不能让一段自由文本直接成为车控程序。因此历史 Trip/操作 Episode 保存事实，条件 Preference 拟单独保存在 conditional_preferences，现有 profile_items 继续做开放画像；另建 skill_items 保存受限步骤模板和证据。第一版基于结构化可信完成事件确定性归并，复杂归纳才可选用后台批次 Qwen。多次执行仅形成 candidate，绝不授予自动执行权限。

本地 VehicleMem-Eval 说明 VehicleMemBench 考察多人车控工具调用、条件约束、冲突、指代、纠错和状态变化；但当前 qa_data/*.json 是 Git LFS 指针，尚不能据此列举完整金标动作。来源文件与字段的逐项核对见 讨论记录。

存储取舍 · 车控记忆和 Skill 要不要独立库？

建议先做逻辑隔离、共用现有 PostgreSQL；物理拆库是后续扩容选项。

待确认设计

车控历史、条件 Preference、Skill 分成独立表、Repository 和检索接口：历史按用户/车辆/时间/行程/工具精确查；Preference 按属性/作用域/适用条件查；Skill 按意图/条件/状态查，模糊查询时才使用摘要向量。通用 Event 可引用车控 Episode，但车控执行不能依赖通用向量 Top-K 或自由文本画像。第一版共用 PostgreSQL、事务与 JSON Mirror，可降低运维成本；若后续吞吐、隔离或权限要求证明需要，再迁往独立数据库。

输入边界 · 对话与车控 JSON 并行

已确认输入类型；接口和存储尚待编码。

设计已确认，代码未实现

对话继续进入 /v1/messages 与 Session→Topic→Fact→Event；手机/车机操作建议独立 /v1/vehicle-operations，保存结构化请求、异步执行回执和失败/取消状态，以 operation_id 对齐。两路共享身份、时间和幂等边界，可用明确关联 ID 建证据关系；不能把工具结果当成 assistant 自然语言，更不能把“请求”当成“执行成功”。远程控车允许 trip_id=null；只有成功回执进入成功 Skill Episode。天气/乘员等条件仅取可信上游，随后再进入条件 Preference 与 Skill 候选沉淀。

车控结果与失败兜底

上游提供请求时间、完成时间及明确的成功/失败回执。

待编码

同一 operation_id 合并请求与回执：requested → success | failed | unknown。重复回执幂等；可配置等待时限后仍无回执记为 unknown，迟到回执可更正并审计。失败保留错误码、完成时间和脱敏原因；用户重新发起使用新 operation_id 与可选 retry_of。只有 success 计入成功 Skill 证据；failed/unknown 不可被描述为“已完成”。记忆侧只负责存储、超时、对账和审计，物理车控的重试/补偿仍由上游根据授权及实时车况决定，记忆系统不自行重试车控。

车控 Episode：连续操作如何分组

第一版依赖明确的上游交互分组键；相近时间不等于相同意图。

待确认设计

同一用户、车辆和 interaction_id（或 command_group_id）内的独立 operation_id 组成一个 Episode；trip_id 只是行程关联，不是强制分组键。无分组键时一条操作就是一个 Episode，避免把偶然相邻的空调、车窗、充电动作拼成 Skill。Episode 保存步骤顺序、请求/完成时间、成功/失败/unknown 结果和来源 ID；失败步骤不丢弃，晚到回执更新版本与证据。例：同一组内 07:30 空调 22℃成功、07:31 座椅加热 2 档成功，可作为一个舒适设置候选 Skill 的证据；07:40 无分组键的开窗另存。借鉴 FluxMem 的成败轨迹与 Episode→Skill 来源关系，但第一版不用 LLM 逐条判断分组。

修正 · 上游没有 Topic/interaction ID 也可工作

上一节的 interaction_id 只是可选强证据，不是输入前提。

待确认设计

每条 operation_id 先独立保存请求、结果、时间和作用域；无须对话 topic_id。后台在同一用户/车辆内按时间形成可配置的候选活动窗口，窗口只缩小分析范围，不自动证明相同意图。不同日反复出现、顺序和条件相容且有真实成功回执的操作序列，才能晋升为多步 Skill 候选；单步操作本身也可形成偏好或单步 Skill 候选。自然语言名称可在候选形成后用一次批次 LLM 生成，但步骤必须来自原始 Operation Event。缺少分组或重复证据时保持独立操作，不编造组合流程。

参考 FluxMem 的 Episode→Skill 来源边、memU 的不做/更新/新增、MIRIX 的结构化步骤；以下是 DesayMem 的轻量化改造。

阈值待测试

Operation Episode 先保留真实工具名、参数、条件和回执。相近时间只形成候选窗口；跨独立日/行程重复、同样顺序且成功的序列才累积证据。测试初值为 3 次独立成功后形成 candidate，近期失败、撤销或用户否定使其暂停；具体阈值均为超参数。相同流程优先更新旧 Skill，条件冲突时共存或分开，不任意覆盖。参数随季节变化优先交给条件 Preference：例如冬季 22℃、夏季 24℃共用“空调→座椅”流程。单步固定数值默认只进 Preference；显式快捷操作或跨工具流程才值得单建 Skill。首版用代码统计与归并，复杂候选命名才可选一次后台批次 Qwen；candidate 只用于建议/确认，自动执行权限仍由上游控制。

例：U1 在 V1 的三个独立冬季工作日均成功执行空调 22℃→座椅加热 2 档，形成候选并连回六条操作证据；第四天座椅步骤失败应留作反证，不得冒充成功。详细参考与原因见 设计讨论记录。

Hermes 自进化的位置：离线改进，不直达车控

待核对同事具体实现；此处只标注可借鉴的架构边界。

可插拔后续阶段

Hermes Agent 可从会话创建、修改 Skill 文档并设置写入审核；Hermes Self-Evolution 进一步用执行轨迹生成候选并做评测/门槛检查。我们保留独立的结构化 skill_items 作为在线车控候选，只在离线把脱敏 Episode、失败和纠错送入可插拔 Hermes Evolver。其输出必须经工具/参数 Schema、证据、旧版对照、车控回放与人工/受控发布，不能直接修改线上步骤或授予自动执行权限；首次可只优化 Agent 的检索和确认提示。离线运行频率可控，不增加每次车控的在线 Qwen 调用。同事具体采用原生 Skill、memU 桥接或 GEPA 项目尚待看代码确认。

Skill 自进化的发布门槛

借鉴 Hermes 的暂存审核与候选评测，增加车控专有的结构化与权限边界。

待确认设计

observed 是统计而非 Skill；达到阈值创建 candidate，通过校验/回放/审核后为 published（可推荐，非自动执行授权）；失败、纠错或证据撤销可 suspended，旧版可 retired。Hermes 第一版只建议名称、说明与确认话术的改动，不直接改工具、顺序、参数来源、conditions、scope、证据或权限；步骤改动必须提交新的结构化版本并重新验证。发布时旧 v1 保持可用直到 v2 通过 Schema/白名单/身份/条件/证据检查和多人、失败、冲突案例离线回放，再原子切换当前版本；保留 v1 以便回滚，并同步 JSON Mirror。参考 Hermes Skills 审核 与 Hermes Self-Evolution 的候选评测，车控执行权限始终由上游独立管理。

Skill 在线检索与消费边界

借鉴 memU 的短描述按需加载、MIRIX 的摘要/步骤分离与 FluxMem 的来源关联；车控安全由我们另加边界。

待确认设计

规范化意图优先按 published + user/vehicle scope + intent + conditions 精确读取；口语模糊时复用 BGE 摘要匹配及已有 Planner，不全量注入 Skill。当前天气/乘员等条件未知时不默认匹配受限 Skill；当前用户明确参数高于历史 Preference。读取命中 Skill 后再按条件取 Preference 补全参数，缺少值或车辆不支持工具时返回需要确认/不支持，不编造调用。结果只包含 skill_id/version/steps/parameter_sources/conditions/evidence_ids/missing_inputs 等建议数据；记忆系统不执行车控，权限、安全和确认均由上游在实时车况下决策，执行回执再回写 Operation Event。candidate/suspended/retired 不进入正常在线候选。

条件 Preference：同一属性允许多个有效值

参考 AWS Preference 的上下文记录与本地画像调研；DesayMem 增加车控参数选择和冲突兜底。

待确认设计

profile_items 一行保存一个 attribute + value_json + conditions + scope + 有效期 + 证据。例如 U1/V1 冬季工作日 22℃、夏季工作日 24℃可共存。运行时用可信用户/车辆/时间/天气等条件精确筛选；条件未知不当作满足。用户本轮明确值优先于历史值，车辆能力与上游安全策略必须通过；若多个同样适用的值仍冲突，返回候选及证据并询问用户，不让 LLM 猜。弱行为观察可用于推荐，不能无确认地变成车控精确参数。属性/作用域索引与 JSONB 条件校验即可完成常规查询，不增加在线 Qwen。参考 AWS User Preference；详情同步至 讨论记录。

历史行程 → 通勤习惯候选

借鉴 AWS Episodic Memory 的“具体经历先存、跨经历再发现模式”；我们用结构化行程与低成本统计实现。

待确认设计

每个 trip_id 独立保存用户/驾驶员/车辆、出发/到达时间、必要的可信地点标签和状态；不在记忆库保存完整 GPS 轨迹。车控 Operation Event 可关联 trip_id，远程控车也允许为空。后台按工作日/周末、车辆和可信地点分组统计出发时段、常用车及覆盖天数，形成带来源 trip IDs 的 observed_habit；“近期常在 7:20–7:40 驾驶 V1 出发”是观察，不等于“希望 7:30 自动出发”或“最喜欢 V1”。只有用户明确要求提醒/自动化，且上游确认授权，才可转成相应配置。普通统计不用每次 Qwen 或向量，历史行程与候选表均按数据库行同步 JSON Mirror。参考 AWS Episodic Memory，详细取舍见 讨论记录。

充电、泊车与远程控车：统一事实层，分域安全策略

借鉴 Episode、Preference、Procedure 分层；车控权限、设备能力和实时安全条件由我们划清系统边界。

待确认设计

三类操作共用 operation_id + source + tool + args + request/completion time + result 的 Operation Event，不各造事实库。充电目标电量、常用站点、泊车区域、远程预冷等可沉淀为带用户/车辆/时间/天气条件的 Preference 或观察习惯；“到站→开始充电”“出发前预冷”等重复成功流程可形成 Skill 候选，但次数不等于授权。支付、车位与桩可用性、车辆在线、手机用户权限及车窗/泊车的实时安全条件均由上游 Tool Registry/Policy 检查；记忆系统只返回参数与证据，不自行执行。失败/unknown 不算成功 Skill 证据；精细位置与遥测不在记忆库长期保存，普通回执不新增 Qwen 调用。

泛化边界：例子不是固定 Schema

空调/充电/泊车只是解释性样例；通用模型不按设备类别增加独立记忆表。

设计澄清

统一 Operation Event 保存 tool_name + typed args + request/result + time + scope + context；统一 Preference Item 保存 attribute + typed value + conditions + evidence；统一 Skill Item 保存 intent + ordered tool references + parameter bindings + conditions + evidence。可扩展 Tool/Attribute Registry 提供执行相关的类型、单位、范围和能力校验，不是关键词规则；新车控工具主要扩展 Registry 与测试，不改通用流水线。无法映射成已注册工具或明确参数的模型候选可用于人工讨论，不得成为可执行 Skill。自然语言语义理解交给模型/向量，身份、证据与安全边界由代码和上游策略确定。

主动服务 / 通知 / 免打扰：记忆提供偏好，上游决定发送

不新建专用记忆类型；沿用通用条件 Preference 与证据链。

第一版范围待确认

用户明确的通知时间窗、渠道、频率、免打扰和主动服务许可可保存为带 scope/conditions/validity/evidence 的 Preference；忽略一次通知只是弱观察，不自动改开关。上游主动服务引擎根据实时事件查询当前适用偏好，再核验授权、必要通知优先级与频率限制，决定是否发送。第一版记忆系统只实现沉淀和被动查询，不自带调度器、推送或主动决策；参考 AWS User Preference 的偏好提取/合并，执行边界由 DesayMem 车载场景额外规定。

Skill / Preference 与执行权限严格分离

参考系统解决“记住/改进如何做”；自动车控的授权与实时安全由上游负责。

待确认契约

记忆只返回 Skill/Preference 候选、条件、证据和版本；published 意味着可推荐，不意味着授权执行。上游 Policy/Permission 是按用户、车辆、工具能力、条件和有效期维护授权/确认/撤销的唯一事实源，并实时检查车况与工具能力。用户说“以后自动预冷”可形成明确意向，但必须走上游授权流程；撤销后立即禁止自动执行，历史 Episode 仍保留为事实。缺身份、条件、参数或授权时默认不执行，必要时询问确认。每次决策及回执关联使用的 Skill/Preference ID 与版本，便于审计和回放；不同工具的安全策略通过上游 Registry/Policy 配置，不在记忆系统硬编码车控类型。

纠错、撤销与删除：三种不同的传播路径

借鉴 Mem0 的记忆变更、MIRIX 的 Procedure 更新与 Hermes 版本审核；DesayMem 追加跨层证据失效。

待确认设计

偏好纠错使同条件旧值失效、新值留版本和证据，历史真实操作不重写；依赖旧值的 Skill 重新取参或暂停。撤销自动化由上游 Permission 立即生效，记忆侧同步暂停相关建议，历史成功操作不能恢复授权。隐私删除则按经验证的范围阻止召回，清除 Trip/Operation 与依赖证据的习惯、Preference、Skill/Profile，并同步 JSON Mirror/缓存及可控备份。所有衍生项保留来源 ID，先标记 stale/suspended，再按受影响范围后台重算，避免全量反复调用 Qwen；不可逆删除与权限撤销必须走有身份验证的专用入口。
