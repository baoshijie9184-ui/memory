写入七步流水线（infer=true）

代码入口 memory.py::add。对话进来后，先读取上下文（最近消息 + 已有记忆 + L3 画像），交给 LLM 做 ADD-only 抽取，去重后写入 L1， 再做实体链接和消息保存。Step 5 写入 L1 是核心检查点——之后立即触发派生层构建（见下页）。

ADD-only 原则：LLM 只能生成新事实，不能 UPDATE/DELETE。偏好"改为 26 度"会存成一条新 L1，旧"22 度"不删，靠检索期冲突消解过滤。

L1 → L2 → L3 派生层构建

代码入口 memory.py::_evolve_layers，在 L1 写入成功后 best-effort 触发。L2 和 L3 并行构建，互不依赖，任一失败只记 warning，不回滚 L1。

L2 EpisodeBuilder：读同 scope 的 active episode → LLM 判断 continues/新建 → 写事件摘要（含 source_memory_ids 指回 L1）。
L3 ProfileDistiller：L1 + 向量近邻组成证据簇 → LLM 输出 beliefs → Python 校验证据 ID → 执行 CREATE/CONFIRM/SUPERSEDE → 拼成 narrative 反馈下一轮抽取。

三层记忆模型：L1 / L2 / L3

L1 是事实真源，ADD-only 不可变。L2 和 L3 都从 L1 派生，可重建。LLM 只提 JSON 建议，Python 校验后写库。
L2 和 L1 存同一张 memory_items（要参与向量召回），L3 存独立表 profile_beliefs（主键直读，不进 HNSW 索引）。
层级存什么存哪怎么读可重建
L1 Fact自包含原子事实memory_items, semantic_memory向量 + BM25 + 实体 + 时间真源
L2 Episode一次经历的摘要同一张 memory_items, episodic_memory与 L1 一起向量召回可由 L1 重建
L3 Profile当前有效信念/偏好独立表 profile_beliefs按 tenant+user 主键直读可由 L1/L2 重建
为什么 L2 和 L3 存放位置不同？
L2 要能被"上次那次去公园"语义召回，所以要有 embedding，和 L1 共用 pgvector HNSW 索引。
L3 回答"这个人现在是什么样"，访问方式是主键读取不是 cosine top-k。如果把信念也写成普通向量行，稳定画像会被一年海量事实淹没。

部署形态：前后端分离

Docker Compose 运行 postgres + api 两容器。API 映射到 127.0.0.1:8766，默认不暴露公网。
LLM Proxy 是独立 FastAPI 服务，隔离模型密钥。前端拿到记忆 API 的 search 结果后，把 memory_context 发给 Proxy 生成最终对话回复。
