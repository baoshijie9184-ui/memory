## 1. 冒烟结果矩阵

### 1.1 locomo

**数据与存储**：datasets/locomo/locomo10.json（10 对话，~1986 题，Cat1 单跳 18.3% / Cat2 时序 20.8% / Cat3 开放 6.2% / Cat4 多跳 54.6%）；记忆库 data/lightmem/qdrant_post_update/（conv-26/30/41…）。

**指标与计算**（metrics/official.py locomo_f1_score，对齐官方）：
- **Token-level F1**：pred 与 gold 先 normalize（小写、去冠词、去标点、空格归一）+ Porter 词干，再按 token 集合算 precision/recall/F1
- **ACC 口径**：Cat1/2/3 题目 F1≥0.5 记正确，Cat4 多跳 F1≥1.0（完全匹配）记正确
- LightMem 自家管线全量另用 LLM judge（judge_correct），与 F1 口径不同——所以两个入口数字差异大（65.39% vs 16.5%）

**全量**（2026-09-13，LightMem 管线完整跑，1540 题 / 448 万 token）：

### 1.5 desaymem

**数据与存储**：datasets/DesayMem_multitenant_benchmark/data/（tenants/ 三级层级 814 sessions + eval_cases.json 26 用例）；记忆库 data/lightmem/qdrant_new_datasets/qdrant_post_update/desaymem_*（10 collection）。

**指标与计算**（desaymem_adapter，断言式非 QA）：
- **strict**：检索结果关键词子串判定——must 全部命中、must_not 全不出现、not_top1 不在第一行（对齐官方 must/must_not/not_top1 语义）

- 汇总 ACC = 通过用例 / 26（SKIP 的 flt_04 不计入分母时按 25 算，结果矩阵以日志为准）

### 2.1 全量一键脚本 — `scripts/run_full.sh`

只改脚本顶部 3 个变量即可切换：

```bash
MEMORY_SYSTEM="structmem"                # none / mem0 / structmem / structmem-nosummary
DATASET="carmem"                        # locomo / vehiclemembench / longmemeval / carmem / desaymem
MODEL_CONFIG="memory-llm"               # models.yaml 的 key
```

然后 `./scripts/run_full.sh`。结果自动归档到统一 results 仓库：`results/raw/{时间戳}_{数据集}_{系统}_{模型}/`。

**不同算法差异配置**走 per-system 覆盖文件：`config/systems/{系统名}.env`（脚本自动 source；现仅 structmem 有——控制建库管线 LLM；none/mem0 无需）。评测端模型统一 `--model-config`（models.yaml）。GPU 仅建库阶段用（本地 llmlingua-2/bge-m3），评测纯 API；可用 `GPU_ID` 变量手动指定。

**.env 环境分工机制**（算法差异配置 + python 环境，一个文件全包）：

| envs/ 环境 | 分工 | 谁在用 |
|---|---|---|
| `envs/eval` | 评测进程 run.py（纯 API 调用；mem0ai 2.0.20 从此可编辑安装指回 systems/mem0） | 所有系统的评测 |
| `envs/lightmem` | structmem 建库（lightmem/tiktoken/qdrant_client + 本地 GPU 模型） | build_lightmem_lib.py |
| `envs/desaymem` | DesayMem 自家 HTTP 后端 | 评测不用 |

`.env` 可配置的变量（新算法接入时在其 `config/systems/{算法名}.env` 写，主脚本零改动）：
- `PY_EVAL`：覆盖评测进程 python（默认 envs/eval）
- `PY_BUILD`：覆盖建库进程 python（默认 envs/lightmem）
- `LIGHTMEM_API_BASE/KEY/MODEL`：structmem 建库管线 LLM
- 任意算法专属变量（bridge/建库脚本里 os.environ 读）

脚本启动时打印 `评测环境: ... | 建库环境: ...` 供确认。脚本自动处理：
- **mem0/none**：跳过建库直接评测
- **structmem 系**：先逐样本建离线库（**断点续跑**——已建 collection 自动跳过，中断重跑即可；自动选空闲 GPU；locomo 用已有全量库自动跳过）→ 再评测
- **评测**：`--full` 全量，明细落 `datasets/VehicleMem-Eval/results/{数据集}_{模型}_{系统}_{时间戳}.json/.txt`
- **日志**：`$RESULT_DIR/run_full_*.log`（建库+评测全程）
- 跑完提示追加结果到本表 §2

注意：locomo × structmem 想复现 65.39% 那次结果，用的是 LightMem 自家管线入口（`run_full_pipeline.sh`，见 LightMem-LoCoMo全量测试指南.md），不是本脚本。

## 3. 结论与观察

1. **structmem ≈ structmem-nosummary 全程一致**：summary 层未生效（时间窗 3600s 对跨月数据不产摘要）。全量想让 summary 起作用需 `--summary-time-window 604800` 重建
2. **carmem 上 none(68%) > mem0(66%) > structmem(54%)**：该数据集 QA 偏常识，记忆增益有限；structmem 低还有 user_1+ 库缺失回退问题
3. **desaymem 是唯一抓到 LightMem 真缺陷的数据集**：抽取层丢实体/数值/改语言，隔离维度 8/9 PASS（collection 级隔离天然成立）
4. **vehiclemembench 对所有系统都难**（tool_f1 最高 8.48%）：工具参数检索是共性短板
5. 冒烟阶段库规模差异大（carmem 22 条 vs vmb 264 条），全量后数字会明显变化，本矩阵数字仅代表"链路跑通"
