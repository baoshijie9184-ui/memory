# Mem0 + LoCoMo 评测问题与修复记录



## 1. 目标与范围

本文记录 Mem0 评测 LoCoMo 时定位到的数据库、记忆行为统计、清理流程和 Token 分阶段记账问题。修复版使用独立入口和独立数据库，不替换原 `memory_bridges.py` 中的 Mem0 实现。

涉及文件：

- `datasets/VehicleMem-Eval/evalcore/memory_bridges_fixed.py`
- `datasets/VehicleMem-Eval/run_fixed.py`
- `datasets/VehicleMem-Eval/evalcore/eval_engine.py`

## 2. 问题总览

| 问题 | 表现 | 原因 | 状态 |
| --- | --- | --- | --- |
| 读取错误的 `history.db` | 报告显示 `ADD=9750 / DELETE=8949` | 服务器旧代码写死读取 `~/.mem0/history.db` | 已在固定版隔离 |

## 3. `history.db` 统计源错误

### 3.1 现象

旧报告显示：

```text
事件分布: ADD=9750 DELETE=8949
删除占比: 47.86%
```

但对本次全量运行的真实数据库查询得到：

```text
/tmp/mem0-full-1789547778/history.db
ADD=4817 DELETE=4817
```

两组数字不一致，说明报告没有读取当次运行的数据库。

### 3.2 修改前

服务器旧版 `behavior_stats()` 写死读取 root 用户的全局库：

```python
dbs = glob.glob(os.path.expanduser("~/.mem0/history.db"))
```

实际运行命令设置了：

```bash
MEM0_DIR=/tmp/mem0-full-<timestamp>
```

因此 Mem0 实际写入 `/tmp/mem0-full-<timestamp>/history.db`，而报告却读取 `/root/.mem0/history.db`。

### 3.3 修改后

固定版显式指定历史库：

```python
self._history_db_path = os.path.join(storage_root, "history_fixed.db")

cfg = {
    "history_db_path": self._history_db_path,
    # llm / embedder / vector_store ...
}
```

统计只查询这个已知路径：

```python
def _raw_event_counts(self) -> dict:
    if not os.path.isfile(self._history_db_path):
        return {}
    with sqlite3.connect(self._history_db_path) as conn:
        return {
            event: count
            for event, count in conn.execute(
                "SELECT event, COUNT(*) FROM history GROUP BY event"
            )
            if event
        }
```

## 4. 样本结束清理污染 DELETE 统计

### 4.1 现象

10 轮和 20 轮冒烟测试的原始库分别出现：

```text
10 轮: ADD=12 DELETE=12
20 轮: ADD=30 DELETE=30
```

DELETE 记录在 QA 完成后的数秒内连续产生，且 `memory_id` 与 ADD 一一对应。这些是框架清理，不是 Mem0 冲突消解。

### 4.2 修改前

```python
def delete_memoryos_user(self, uid):
    self._m.delete_all(user_id=uid)
```

`delete_all()` 会删除 Qdrant 中的当前用户记忆，并在 `history.db` 中为每条记忆写入 DELETE 审计记录。

### 4.3 官方项目依据

`D:\UID05975\soft\Memory\memory-benchmarks` 中的 LoCoMo runner：

```python
user_id = f"locomo_{conv_idx}_{run_id}"
```

它通过 `conv_idx + run_id` 隔离数据。样本 QA 完成后直接统计指标，没有调用 `delete_user()`。客户端虽然定义了删除接口，但 LoCoMo 评测流程没有调用。

### 4.4 修改后

固定版与官方行为对齐，样本结束不删除：

```python
def delete_memoryos_user(self, uid):
    # Samples are isolated by user_id and remain available for inspection.
    return None
```

结果：

- 样本间通过 `user_0`、`user_1` 等 ID 隔离。
- 测试结束后 Qdrant 仍保留本轮记忆，便于调试。
- `history_fixed.db` 中的 DELETE 只来自 Mem0 自身的冲突处理。
- 数据库原始事件和最终报告数字一致，不再需要扣除清理事件。

## 5. 独立数据库和运行入口

### 5.1 修改前

原始入口固定加载原桥接：

```python

```

原 Mem0 使用：

```text

```

### 5.2 修改后

新建 `run_fixed.py`，只在该进程内把构建函数指向固定版：

```python
from evalcore import eval_engine as _eval_engine
from evalcore.memory_bridges_fixed import (
    MEMORY_SYSTEMS,
    build_memory_system as _build_fixed_memory_system,

_eval_engine._build_from_registry = _build_fixed_memory_system

```

固定版使用独立目录：

```python
storage_root = os.path.join(
    root, "results", "mem_data", f"mem0_fixed_{model_cfg.name}"

```

完整路径：

```text
datasets/VehicleMem-Eval/results/mem_data/mem0_fixed_memory-llm/
├── history_fixed.db
├── meta.json
└── collection/
    ├── eval_mem0
    └── eval_mem0_entities
```

每次固定版评测开始前只重建固定版目录：


这会删除上一次固定版运行，但不会修改以下数据：

```text

```

## 6. LoCoMo 评测协议与 Judge Token 误记

### 6.1 本地存在的两套 LoCoMo 协议

LoCoMo 不只有一种评测方式。当前两个项目分别实现了不同协议，结果不能直接混在一起比较。

#### A. VehicleMem-Eval Token-F1 协议

`datasets/VehicleMem-Eval/adapters/locomo_adapter.py` 当前实现：

```python
f1 = locomo_qa_score(pred, gold, cat)
return {"correct": correct, "score": f1, "metric": "f1"}
```

特点：

- 评测全部 1986 道问题。
- 类别 1–4 使用 Token-F1/多跳 F1。
- 类别 5 共 446 道对抗问题，使用拒答匹配。
- `evaluate_answer()` 本身不调用 LLM Judge。

#### B. mem0ai/memory-benchmarks J-score 协议

`D:\UID05975\soft\Memory\memory-benchmarks\benchmarks\locomo\run.py` 实现 answer + judge 流程：

```python
raw = await judge_llm.generate_structured(
    system=JUDGE_SYSTEM_PROMPT,
    user=judge_prompt,
)
correct = raw.get("label", "").upper() == "CORRECT"
score = 1.0 if correct else 0.0
```

特点：

- 使用二值 LLM Judge：`CORRECT` / `WRONG`。
- 评测类别 1–4，共 1540 道问题。
- 类别 5 对抗问题共 446 道，在该 J-score 实现中排除。
- 默认对 top-k `10,20,50,200` 分别生成答案并调用 Judge。
- 真实 Judge 调用应同时存在 Token In 和 Token Out。

### 6.2 本次现象

```text
judge  Token In=34,767  Token Out=0  Calls=9,754  Runtime=441.3s
```

本次命令运行的是 VehicleMem-Eval Token-F1 协议，不是 `memory-benchmarks` J-score 协议。当前 `locomo_adapter.evaluate_answer()` 只执行 `locomo_qa_score()`。`Token Out=0` 且单次输入极少，也表明这 9754 次不是真实 Judge 生成。

### 6.3 修改前

`eval_engine.py` 对所有数据集都无条件设置 Judge 阶段：

```python
llm.set_phase("judge")
result = adapter.evaluate_answer(
    pred, q["answer"], llm, question=q["query"], query=q,
)
```

当前 F1 适配器的 `evaluate_answer()` 没有发起 LLM 请求，但 phase 仍停留在 `judge`。后续 Mem0 清理和 Embedding 请求因此被误记。

### 6.4 修改后

移除无条件 Judge 标记：

```python
result = adapter.evaluate_answer(
    pred, q["answer"], llm, question=q["query"], query=q,
)
```

对可能存在的清理请求使用独立阶段：

```python
if mem and hasattr(mem, "delete_memoryos_user"):
    llm.set_phase("cleanup")
    mem.delete_memoryos_user(uid)
```

真正的 Judge 协议必须在评分函数中实际调用 Judge 模型。例如 LongMemEval 显式使用：

```python
llm.chat(..., use_judge=True)
```

`CountingLLMClient` 会把 `use_judge=True` 的请求自动记为 `judge`。未来如果在 VehicleMem-Eval 中增加 LoCoMo J-score，也应实际调用 `llm.chat(..., use_judge=True)`，而不是只执行 `set_phase("judge")`。

## 7. extraction JSON 解析失败

### 7.1 现象

全量 3018 次 ingest 中观察到 8 次：

```text
Error parsing extraction response: Unterminated string ...
Error parsing extraction response: Expecting ',' delimiter ...
```

失败率约为 `8 / 3018 = 0.27%`。解析失败时 Mem0 将本次 `extracted_memories` 置为空列表，本轮可能缺失记忆。

### 7.2 现有代码

Mem0 已请求 JSON 输出：

```python
response = self.llm.generate_response(
    messages=[...],
    response_format={"type": "json_object"},
)
```

解析失败后直接放弃本轮：

```python
except Exception as e:
    logger.error(f"Error parsing extraction response: {e}")
    extracted_memories = []
```

### 7.3 建议修复（尚未实施）

1. Mem0 LLM 设置 `temperature=0.0`。
2. 设置足够的输出长度，例如 `max_tokens=2048`。
3. 记录原始 `response`、响应长度和 `finish_reason`。
4. JSON 失败时重试 1–2 次，不建议只通过补括号修复被截断的内容。
5. 确认 OpenAI 兼容推理服务真正实施 `response_format=json_object` 约束，而不是仅接受参数。

## 8. 不影响正确性的警告

### 8.1 spaCy / Click

```text
DeprecationWarning: Importing 'parser.split_arg_string' is deprecated
```

这是 spaCy 3.7.5 使用 Click 旧导入路径的弃用提示。当前 spaCy 模型能正常加载，不会导致 extraction JSON 失败，也不影响本次评分。

### 8.2 Qdrant local payload index

```text
UserWarning: Payload indexes have no effect in the local Qdrant.
```

本地 Qdrant 仍支持向量检索和 `user_id` 过滤，只是不使用 payload 索引加速。警告影响性能，不影响检索语义。

## 11. 验收标准

1. `run.py --memory-system mem0` 仍使用原 `memory_bridges.py`。
2. `run_fixed.py --memory-system mem0` 使用 `memory_bridges_fixed.py`。
3. 固定版只读写 `mem0_fixed_<model>/history_fixed.db`。
4. 测试结束后 Qdrant 仍保留本轮记忆。
5. `history_fixed.db` 不再因样本结束清理产生批量 DELETE。
6. LoCoMo Token-F1 协议的效率表中 Judge Token 为 0。
7. LongMemEval 或未来 LoCoMo J-score 使用 `use_judge=True` 时，应正确统计 Judge Token In/Out。
8. 下一次固定版评测开始时，只重建固定版存储目录，不影响原 Mem0 数据。
