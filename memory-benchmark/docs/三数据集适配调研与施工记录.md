## 1. LongMemEval_S（🔶 代码就绪，数据待拉）

### 1.1 数据结构（schema 由 LightMem 仓库同内容副本实证）

顶层 list，每元素 9 字段：
```
question_id            "e47becba"（abstention 题带 _abs 后缀）
question_type          6类: single-session-user / single-session-assistant /
                       multi-session / multi-session-user / multi-session-assistant / abstention
question               "What degree did I graduate with?"
question_date          "2023-05-30 (Tue) 23:40"   ← 时间推理参照点
answer                 "Business Administration"
answer_session_ids     ["answer_280352e9"]
haystack_dates         [53 个 session 时间戳，与 sessions 一一对应]
haystack_session_ids   [53 个]
haystack_sessions      [[{role, content}, ...] × 53]  ← 海量干扰 session
```

- 单题携带 ~53 个 session 的完整 haystack（干扰项远多于答案项），500 题全集 262 MB
- adapter（`adapters/longmemeval_adapter.py`）把 haystack_dates 解析为每条消息 timestamp

### 1.2 考察目标

- **跨 session 记忆**：答句藏在 53 个 session 之一，考验记忆系统对长程多 session 信息的留存
- **6 类细分**：single-session（user/assistant 侧）、multi-session（跨 session 融合）、abstention（识别不可答）
- 官方指标：**yes/no LLM judge**（`metrics/official.py` 已内置官方 judge prompt 全文，含 temporal-reasoning 的 off-by-one 豁免、knowledge-update 的旧信息+新答案容忍、abstention 判分）
- 与 LoCoMo 互补：LoCoMo 是双人闲聊对话记忆，LongMemEval 是用户-assistant 交互记忆（更贴近车机场景）

### 1.3 适配状态

- adapter ✅（build_history/get_queries/evaluate_answer 完整，question_date 已透传给 QA prompt）
- 评分 ✅（官方 judge prompt 三分支已内置）
- bridge 复用 ✅（窄接口通用，mem0/structmem bridge 无需改动——add_memory 逐 session 喂入即可）
- **待验证**：数据拉取后跑 1 题（single 冒烟文件 557 KB）→ 500 题全量。judge 模型本机用 memory-llm

### 1.4 跑法（数据到位后）

```bash
run.py --dataset longmemeval --memory-system mem0 --model-config memory-llm --sample-limit 1   # 先1题
run.py --dataset longmemeval --memory-system mem0 --model-config memory-llm --full             # 500题
```

注意：500 题每题 53 session 的 add 成本极高（mem0 每 session 多 turn LLM 抽取），预计远超 LoCoMo；建议先用 structmem（库直读）或 --build-limit 控制冒烟。

## 2. CarMem（🔶 代码就绪，数据待拉）

### 2.1 数据结构（由 adapter 反推，1.9 MB，100 用户 × 10 偏好）

```
顶层: user_preferences（偏好定义体系） + data（偏好实例列表）
data[i]:
  extraction_conversation  [[{"USER": "...", "ASSISTANT": "..."}, ...], ...]  ← 大写键
  user_preference          gold "Main; Sub; Detail; Attribute" 分号分隔
  next_conversation_question        检索阶段 query
  maintenance_questions    {question_equal_preference / question_negate_preference /
                            question_different_preference / different_attribute}
```

### 2.2 考察目标（三阶段官方协议，COLING 2025 / arxiv 2501.09645）

1. **Extraction** — 从对话抽出偏好，In-Schema F1（预测 Main/Sub/Detail/Attribute 四字段）
2. **Retrieval** — 用 next_conversation_question 检索，hit@k（gold 偏好是否进 top-5）
3. **Maintenance** — 偏好维护动作分类：equal→Pass、negate→Update、different→(MP)Append/(SP)Update
   考察记忆系统的**增量更新/冲突消解**能力——这正是 add_memory 接口里 UPDATE/DELETE 事件的用武之地，mem0 的事件驱动机制理论上强项

### 2.3 适配状态

- adapter ✅（eval_protocol="carmem" 走 run_official_eval 三阶段分支，eval_engine 已有对应调度）
- 评分 ✅（official.py 内置三阶段评分）
- **bridge 适配点（关键差异）**：CarMem 不是 QA 式——extraction 需要系统在 add 后能**吐出结构化偏好**，超出"检索文本→作答"的窄接口。当前 bridge 契约只覆盖 retrieval 阶段；extraction/maintenance 需要评审 adapter.run_official_eval 的具体调用方式后决定是否扩展接口（可能给 bridge 加 get_structured_preference 可选方法）。**待数据拉取后对代码逐段核验**
- 100 用户 × 10 偏好 × add 成本中等（对话较短）

### 2.4 跑法

```bash
run.py --dataset carmem --memory-system mem0 --model-config memory-llm            # 冒烟 5用户×2偏好
run.py --dataset carmem --memory-system mem0 --model-config memory-llm --full     # 全量
```

### DS-3 | 2026-09-14 | vehiclemembench 冒烟第一轮 F1=0 根因与 prompt 修复

**第一轮冒烟**（`--build-limit 200`，file_range 默认 1，即 qa_1.json 10 题）：管道全通（build 43 分钟 218 条 → QA 10 题 → Tool F1 报告），但 **Tool F1 = 0.00%（0/10）**，所有类别全 0。

### 7.2 全量建库（第一/二/…个终端）
评测端 uid 是 `user_{idx}`，对应 collection `{dataset}_user_{idx}`，所以必须逐样本建：

```bash
cd /data/pengshuang/memory-benchmark/systems/LightMem/experiments/locomo
export TIKTOKEN_CACHE_DIR=/data/pengshuang/memory-benchmark/tmp/tiktoken_cache
PY=/data/pengshuang/memory-benchmark/envs/lightmem/bin/python

# carmem: 100 个样本
for i in $(seq 0 99); do
  $PY -B -u build_lightmem_lib.py --dataset carmem --sample-idx $i --turn-limit 0 \
      --extraction-mode event --enable-summary || break
done

# vehiclemembench: 50 个样本
for i in $(seq 0 49); do
  $PY -B -u build_lightmem_lib.py --dataset vehiclemembench --sample-idx $i --turn-limit 0 \
      --extraction-mode event --enable-summary || break
done

# longmemeval: 500 个样本（最重，建议 nohup 挂后台）
nohup bash -c 'for i in $(seq 0 499); do \
  /data/pengshuang/memory-benchmark/envs/lightmem/bin/python -B -u build_lightmem_lib.py \
  --dataset longmemeval --sample-idx $i --turn-limit 0 \
  --extraction-mode event --enable-summary || break; done' > /tmp/build_lme_full.log 2>&1 &
```

注意：
- 微量冒烟已建过 `{ds}_user_0`，**重复跑 --sample-idx 0 会重建/覆盖**，无碍
- 已建的样本跳过即可（看 `data/lightmem/qdrant_new_datasets/qdrant_post_update/` 下有哪些 `{ds}_user_N`）
- 估算：LightMem 建库很快（200 轮约 8.5 分钟），carmem 每用户 22 轮秒级；lme 每 session 几百轮，500 个估数小时，建议晚上挂
- summary 层说明：--summary-time-window 默认 3600s 对跨月数据不产摘要。想让 structmem 的 summary 层全量生效，改成按天/周（如 `--summary-time-window 604800`）再重建；否则 structmem 与 structmem-nosummary 全量结果会一样
- 用 `--extraction-mode flat` 可另建一套真 lightmem 库（换个 LIGHTMEM_COLLECTION_PREFIX，见 7.3 命名）
