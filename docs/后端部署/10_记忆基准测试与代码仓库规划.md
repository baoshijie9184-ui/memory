# 服务器目录说明与记忆基准仓库规划

## 1. 总体边界

服务器内容分成两个完全独立的区域：

```text
/data/pengshuang/
├── desaymem/              # 在线后端部署区，只运行 DesayMem 服务
└── memory-benchmark/      # 记忆基准实验区，统一管理对比项目
```

必须坚持：

- `/data/pengshuang/desaymem/` 只用于当前记忆后端及其依赖服务的部署、运行和持久化；
- `/data/pengshuang/memory-benchmark/` 用于数据集、基准代码、Mem0、MemOS/MemoryOS、实验数据库和结果；
- 基准测试不能读写或清理生产数据库；
- 第三方仓库不能放进 `desaymem/apps/`；
- 两个区域可以共享已启动的 Qwen 和 BGE-M3 API，但不共享业务数据库。

`memory-benchmark` 是推荐名称，也可改为 `memory_benchmark`，选定后保持一致。本文使用前者。

## 2. 现有 `/data/pengshuang/desaymem/` 目录

```text
/data/pengshuang/desaymem/
├── apps/
├── cache/
├── data/
├── envs/
├── logs/
├── models/
└── run/
```

这是一套完整的服务部署目录，各目录作用如下。

### 2.1 `apps/`：在线应用代码

```text
apps/
├── DesayMem_mem0/        # 当前记忆后端 Git 仓库
└── embedding/            # BGE-M3 FastAPI 服务代码
```

- `DesayMem_mem0/` 提供 20142 记忆 API；
- `embedding/` 提供 20141 Embedding API；
- 这里放稳定部署代码，不放 Mem0、MemOS 等对比仓库；
- Git 更新后通常在这里 `git pull` 并重启对应服务。

### 2.2 `cache/`：可重建缓存

用于 Conda、pip、临时构建、vLLM torch.compile 和 FlashInfer 等缓存。它不应保存唯一数据、数据库、最终实验结果或未纳入 Git 的代码。磁盘不足时可以按子目录清理，但不要在服务运行期间无差别删除整个目录。

### 2.3 `data/`：在线服务持久数据

```text
data/
├── postgres/             # PostgreSQL 生产实例的数据目录
└── history.db            # DesayMem SQLite 会话历史
```

- `postgres/` 保存 L1 记忆、向量、实体、Episode 和 Profile 等生产数据；
- `history.db` 保存最近消息和历史；
- 不能提交 Git，不能放 benchmark 数据库；
- 不能对已有 `postgres/` 再执行 `initdb`；
- 删除或覆盖前必须备份并确认目标路径。

### 2.4 `envs/`：部署服务环境

```text
envs/
├── llm/                  # vLLM、PyTorch、Qwen 服务环境
├── embedding/            # SentenceTransformers、BGE-M3 环境
├── backend/              # DesayMem 后端环境
├── postgres/             # PostgreSQL 16、pgvector 环境
└── screen/               # screen 工具环境
```

这些环境已经用于在线服务。benchmark 不应在其中安装 Mem0 或 MemoryOS 依赖，以免引起版本冲突。

### 2.5 `logs/`：在线服务日志

保存 PostgreSQL、后端、Qwen 和 Embedding 的服务日志。它只记录部署服务；benchmark 日志应放入新的实验根目录。后续建议增加日志轮转。

### 2.6 `models/`：部署模型权重

```text
models/
├── Qwen3-32B/
└── bge-m3/
```

这里不放代码、数据库或实验输出。benchmark 如果复用 20140/20141，无需复制模型；某套系统必须使用其他模型时，将实验模型放在 benchmark 独立目录。

### 2.7 `run/`：运行时状态

用于 PostgreSQL socket、PID、锁文件等短生命周期状态，不作为永久数据，不提交 Git。benchmark 使用自己的 `run/`。

## 3. 现有部署区职责汇总

```text
/data/pengshuang/desaymem/
├── apps/                  # 正式服务代码
├── cache/                 # 正式服务可重建缓存
├── data/                  # 正式服务数据库和持久状态
├── envs/                  # 正式服务运行环境
├── logs/                  # 正式服务日志
├── models/                # 正式服务模型
└── run/                   # 正式服务运行时文件
```

| 服务 | 位置/资源 | 端口 |
|---|---|---:|
| Qwen3-32B | `models/Qwen3-32B` + `envs/llm` | 20140 |
| BGE-M3 | `models/bge-m3` + `apps/embedding` | 20141 |
| DesayMem API | `apps/DesayMem_mem0` | 20142 |
| PostgreSQL | `envs/postgres` + `data/postgres` | 20143 |
| SQLite | `data/history.db` | 无端口 |

## 5. 创建目录

这些命令只创建目录，不修改现有部署：

```bash
mkdir -p /data/pengshuang/memory-benchmark/{benchmark,systems,envs,datasets,data,models,configs,secrets,results,logs,cache,run,scripts,docs,backups}
mkdir -p /data/pengshuang/memory-benchmark/systems/{desaymem,mem0,memos,others}
mkdir -p /data/pengshuang/memory-benchmark/envs/{runner,desaymem,mem0,memos}
mkdir -p /data/pengshuang/memory-benchmark/datasets/{incoming,raw,processed,ground_truth,fixtures,manifests}
mkdir -p /data/pengshuang/memory-benchmark/data/{postgres,sqlite,vector_stores,graph_stores}
mkdir -p /data/pengshuang/memory-benchmark/results/{runs,comparisons,reports,exports}
```

如果准备直接 `git clone`，不必预先创建具体仓库目录；让 Git 创建 `benchmark`、`systems/mem0` 等目录即可。

## 6. 代码仓库放置

### 6.1 统一测试框架

建议新建自己的 GitHub 仓库 `DesayMem-Benchmark`，服务器位置：

```text
/data/pengshuang/memory-benchmark/benchmark
```

保存统一数据格式、各系统 adapter、评价指标、运行脚本、小型 fixtures、配置模板和文档。

### 6.2 被测试系统

```text
/data/pengshuang/memory-benchmark/systems/desaymem
/data/pengshuang/memory-benchmark/systems/mem0
/data/pengshuang/memory-benchmark/systems/memos
```

- `systems/desaymem` 是实验副本，不是在线运行的 `desaymem/apps/DesayMem_mem0`；
- 第三方源码尽量保持干净，修改放自己的 fork/分支；
- adapter 优先写在统一 benchmark 仓库；
- “MemoryOS”和“MemOS”可能是不同项目，测试前记录准确论文、仓库 URL、tag 和完整 Git SHA。

示例：

```bash
cd /data/pengshuang/memory-benchmark
git clone <你的DesayMem-Benchmark仓库地址> benchmark
git clone https://github.com/psile/DesayMem_mem0.git systems/desaymem
git clone <Mem0官方仓库地址> systems/mem0
git clone <确认后的MemoryOS或MemOS仓库地址> systems/memos
```

## 7. 环境隔离

每个系统使用独立环境：

```text
memory-benchmark/envs/runner
memory-benchmark/envs/desaymem
memory-benchmark/envs/mem0
memory-benchmark/envs/memos
```

不得把实验依赖安装到生产 `desaymem/envs/llm`、`embedding`、`backend` 或 `postgres`。若第三方依赖冲突，可使用容器，但数据卷只能挂载到 `memory-benchmark/data/<system>`。

## 8. 测试文件管理

新上传文件先进入：

```text
/data/pengshuang/memory-benchmark/datasets/incoming/<批次名>/
```

处理流程：

```text
incoming
  → 格式、隐私、完整性检查
  → 生成 SHA256 和 manifest
  → 原样归档至 raw/<数据集>/<版本>/
  → 标准化至 processed/<数据集>/<版本>/
  → 标准答案放 ground_truth/<数据集>/<版本>/
  → benchmark 只读加载
```

真实用户、车辆、位置和对话数据必须先脱敏。原始数据不在原位置直接修改。

## 9. 数据库隔离

生产 PostgreSQL 是 `127.0.0.1:20143/desaymem`，benchmark 不得连接该生产数据库。

推荐独立 PostgreSQL 实例：

```text
数据目录：/data/pengshuang/memory-benchmark/data/postgres
端口：另选不冲突且获准的端口
数据库：bench_desaymem、bench_mem0、bench_memos
```

短期复用同一 PostgreSQL 进程时，也必须建立独立的 `bench_*` 数据库。清理脚本必须验证数据库名以 `bench_` 开头，禁止对生产库执行清理。

SQLite、Qdrant、Neo4j 等放到：

```text
/data/pengshuang/memory-benchmark/data/<system>/
```

或每次实验独立放在 `results/runs/<run_id>/state/<system>/`。

## 10. 复用模型服务

统一模型赛道可复用：

```text
Qwen：http://127.0.0.1:20140/v1，memory-llm
BGE-M3：http://127.0.0.1:20141/v1，1024维
```

这样无需为每个框架重复加载 32B 模型，也能保证算法对比公平。另设“原生最佳配置赛道”，允许各系统使用官方推荐模型，但两类结果不能混排。

截图显示系统内存充足，但多张 H20 显存已占用约 80–93GB。实验默认调用现有模型 API；新 GPU 任务必须先确认资源归属。GPU4 曾显示 1 次不可纠正 ECC，若计数增加或出现 CUDA/Xid 错误，应联系管理员。

## 11. 统一 Adapter

```python
class MemoryAdapter:
    def health(self) -> dict: ...
    def reset(self, namespace: str) -> None: ...
    def add(self, messages: list[dict], context: dict) -> dict: ...
    def search(self, query: str, context: dict, top_k: int) -> list[dict]: ...
    def get_all(self, context: dict) -> list[dict]: ...
    def delete_all(self, context: dict) -> None: ...
```

统一输出记录 `run_id、case_id、system/version、tenant/user、query、content、score/rank、时间、延迟、token 和 error`。某系统不支持 Episode、Profile 或删除时标记 `unsupported`。

## 12. 实验结果

每次运行创建唯一 `run_id`：

```text
results/runs/20260905_153000_desaymem_temporal_v1/
├── run.yaml
├── environment.txt
├── git_revisions.json
├── dataset_manifest.json
├── requests.jsonl
├── responses.jsonl
├── metrics.json
├── resource.csv
├── logs/
└── state/
```

原始响应与指标分开保存，以便修改评分脚本后重新计算。

## 13. 建议指标

- 通用：Recall@K、Precision@K、MRR、NDCG、提取准确率、遗漏率、幻觉率、重复率；
- 生命周期：写入、更新、删除、遗忘、用户隔离和时序冲突正确率；
- 分层能力：Episode/Profile 正确性；
- 性能：P50/P95/P99 延迟、吞吐、错误率、token、CPU/GPU/内存和存储；
- 车载专项：模糊指令、多用户多乘员、时间地点场景、偏好更新、临时/长期偏好、Skill 蒸馏。

## 14. 推荐实施顺序

1. 保持 `/data/pengshuang/desaymem/` 不变，继续作为在线部署区；
2. 创建 `/data/pengshuang/memory-benchmark/`；
3. 建立 `DesayMem-Benchmark` 统一测试仓库；
4. 上传少量文件到 `datasets/incoming/`；
5. 先完成 DesayMemAdapter，用 20–50 条样本跑通；
6. 固定 JSONL 格式、指标和结果目录；
7. 接入 Mem0 的独立环境和数据库；
8. 明确 MemoryOS/MemOS 准确仓库后再接入；
9. 小规模通过后再运行全年车载数据；
10. 输出质量、性能和资源消耗三类报告。

第一阶段不需要修改或停止当前在线 DesayMem 服务。
