# DesayMem 后端原理与数据流

## 1. 写入流程

```text
对话消息
  → 保存最近消息/历史
  → 检索已有相关记忆用于去重与关联
  → Qwen 提取自包含候选记忆
  → 解析结构化 JSON
  → BGE-M3 生成 1024 维向量
  → 内容哈希去重
  → PostgreSQL 写入 L1 memory_items
  → 可选 Episode 聚合
  → 可选 Profile belief 蒸馏
```

`infer=true` 会让 LLM 从对话中提取记忆；`infer=false` 应只用于调用方明确提供可直接保存内容且后端契约支持的场景。

## 2. 搜索流程

```text
查询文本
  → BGE-M3 查询向量
  → pgvector 相似检索
  → 扩展 Episode 证据
  → 读取用户画像
  → Qwen rerank（启用时）
  → 返回 top_k 记忆和 profile
```

当前前端使用 `top_k=5`。BGE-M3 返回的向量相似度只是召回信号，不应直接解释为业务置信度。

## 3. 分层记忆

- L1：具体事实、偏好、事件，直接可检索。
- L2 Episode：将同一连续经历的多条事实归纳为情节摘要。
- L3 Profile/Belief：跨事件形成相对稳定的画像和偏好信念。

日志出现 `Profile distillation failed; L1 facts were still stored` 时，表示基础事实成功保存，但画像蒸馏失败。它是降级而非整次写入失败，需要单独排查 LLM JSON、Profile 表或提示词。

## 4. 时序和冲突

每条记忆携带 `occurred_at`、`observed_at`、`created_at` 等时间信息。对于“22 度 → 从现在开始 26 度”这类冲突，应综合：

1. 同一实体和属性识别；
2. 明确更新语义（“从现在开始”“改成”）；
3. 发生时间与观测时间；
4. 检索时近期有效值优先；
5. 旧值保留历史但不作为当前偏好首选。

## 5. 为什么输出保留 2000 tokens

当前后端只有一个全局 `LLM_MAX_TOKENS`，同时覆盖提取、Episode、Profile 和其他 JSON 任务。1024 对短事实通常足够，但可能截断较大的 Episode/Profile JSON。因此 16K 上下文下暂时保留 2000。

后续推荐按任务拆分：

```dotenv
LLM_EXTRACTION_MAX_TOKENS=800
LLM_CONFLICT_MAX_TOKENS=600
LLM_RERANK_MAX_TOKENS=400
LLM_EPISODE_MAX_TOKENS=1600
LLM_PROFILE_MAX_TOKENS=2000
```

## 6. 质量保障原则

- 提取结果必须忠于原文，不翻译、不虚构。
- 写入与检索使用相同 embedding 模型。
- 对重复测试使用新用户 ID，避免去重影响观察。
- 测试 L1、Episode、Profile 要分别验证，不能只看 HTTP 201。
- 对模糊指令要同时评估召回、时序有效性和最终回答。
